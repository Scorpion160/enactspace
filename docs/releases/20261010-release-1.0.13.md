## Construire les clients sous PowerShell

Les chemins sont des variables locales; garder les fichiers de defines et de signature hors de Git. Utiliser le checkpoint b152677 ou un descendant contenant le patch. Dans le clone de récupération modifié, ne pas employer reset ou checkout pour récupérer les sources.

```powershell
$repo = 'C:\Users\DIOP\Documents\EnactSpaceRecovery\enactspace-20260927'
$webDefines = Read-Host 'Chemin du fichier prive web-client-defines.json'
& "$repo\tools\build_web_with_firebase.ps1" -DefinesPath $webDefines -FlutterArgs @('--build-name=1.0.13', '--build-number=16')
if (!$?) { throw 'Compilation web echouee.' }
Get-Content "$repo\frontend\build\web\version.json"
Get-FileHash "$repo\frontend\build\web\main.dart.js" -Algorithm SHA256
```

Ce bloc reproduit la version livrée; pour une nouvelle distribution, choisir une nouvelle identité et enregistrer les nouvelles empreintes. La configuration web doit contenir URL API HTTPS, projet Firebase, sender ID, clé/app ID web et clé publique VAPID. Le builder régénère le worker Firebase exclu des checkpoints.

```powershell
$androidDefines = Read-Host 'Chemin du fichier prive android-client-defines.json'
Push-Location "$repo\frontend"
try {
    flutter build apk --release --build-name=1.0.13 --build-number=16 "--dart-define-from-file=$androidDefines"
    if ($LASTEXITCODE -ne 0) { throw 'Compilation Android echouee.' }
    Get-FileHash 'build\app\outputs\flutter-apk\app-release.apk' -Algorithm SHA256
} finally { Pop-Location }
```

Le SHA256 d’une nouvelle compilation peut différer : comparer à l’empreinte approuvée de cette compilation, pas automatiquement à celle de cette release. Les avertissements de versions de packages et de migration Kotlin n’ont pas empêché les builds livrés; traiter les mises à jour séparément.

Pour une prévisualisation, lancer depuis frontend `flutter run -d edge --dart-define-from-file=<chemin-prive>`. Quitter avec q. Un aperçu debug n’est pas une publication.

## Préparer et publier le backend

1. Récupérer le commit exact dans un clone isolé et vérifier HEAD. Une récupération Git Windows a échoué avec schannel/early EOF; une récupération HTTP/1.1 avec filtre de blobs et checkout sparse a permis la préparation. Ne jamais désactiver la vérification TLS.
2. Archiver backend, deploy/Dockerfile.backend et frontend/assets/img/logo_enactus_esp.png depuis la racine. Vérifier le SHA256 sur le VPS, rejeter les chemins absolus, traversées et liens avant extraction.
3. Construire depuis le contexte racine avec le Dockerfile backend et un label de commit. Vérifier pip check puis la configuration, les imports API et le catalogue de migrations.
4. Utiliser un override Compose pour une sonde candidate, sans lancer les dépendances ni les workers. Contrôler PostgreSQL en lecture seule. Ne pas injecter directement le fichier env via docker run : l’interprétation de guillemets a provoqué une URL SQLAlchemy invalide.
5. Acquérir le verrou de publication et sauvegarder la configuration. Vérifier que le fichier Compose et les images n’ont pas changé pendant la préparation.
6. Arrêter API et trois workers; prendre une sauvegarde vérifiée fraîche. Contrôler Result=success, ExecMainStatus=0, passed=true et les indicateurs de nettoyage dans le rapport, ainsi que sa date.
7. Comparer le schéma et le head. Cette release n’a pas requis de migration; ne pas en ajouter automatiquement. Examiner séparément toute évolution de schéma.
8. Remplacer atomiquement les images/version dans Compose en conservant propriétaire et permissions; recréer uniquement les quatre services avec --no-deps --no-build --pull never.
9. Vérifier santé, version et identité effective des images pour les quatre conteneurs, puis la configuration des notifications et l’API HTTPS publique. Enregistrer le reçu.
10. Si échec, rétablir les services compatibles avec le schéma. Un rollback Compose ne restaure pas les données.

Une référence Dockerfile `FROM sha256:...` a été interprétée comme un dépôt Docker Hub. Pour un patch local, utiliser un tag local vérifié, `--pull=false`, et comparer l’image de base avant/après construction.

## Publier le web et installer Android

Le publieur historique vérifié contient des constantes de version/build/SHA256. Pour 1.0.13, sa copie opérationnelle a été adaptée avec contrôle du nombre de substitutions; les cinq tests d’extraction sûre ont réussi avant exécution. Ne pas réutiliser les anciennes constantes pour une nouvelle release.

Vérifier le build, son identité, le script transféré et l’archive; publier avec le publieur contrôlé. Contrôler version.json via HTTPS avec un paramètre unique pour éviter un cache. Tester les routes et le rendu dans le navigateur. Les contrôles HTTP n’attestent pas tous les comportements utilisateurs.

Pour Android : `adb devices -l`, autorisation USB acceptée, comparaison SHA256, `adb -s <device> install -r <apk>`, puis `dumpsys package sn.enactusesp.enactspace` pour versionName/versionCode. Ne pas désinstaller en cas de device unauthorized.
